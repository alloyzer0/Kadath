# ADR-0004: RHI 抽象粒度

  - `ADR-0002`: 构建系统与项目结构
  - `ADR-0003`: 跨语言边界规范

---

## 背景

`Phase 0` 已将 `platform -> rhi -> renderer2d` 确定为 `M0` 的关键路径。
这意味着在真正落地第一个图形后端之前，必须先回答一个问题：

**Kadath 的 RHI 应该抽象到什么程度？**

如果抽象过薄：

- 上层 `renderer2d` 会过早依赖具体后端细节
- 后续更换后端或引入第二后端时，返工成本高
- 平台层、资源层和渲染层边界会变得松散

如果抽象过厚：

- 容易提前构造“高层渲染框架”
- 会把材质、场景、批处理等高层策略错误地下沉到 RHI
- 中间层可能引入难以察觉的性能开销
- 单人项目在 `M0-M2` 会被过度抽象拖慢

因此，本 ADR 的目标不是设计完整渲染架构，而是锁定：

- `RHI` 这一层**负责什么**
- `RHI` **不负责什么**
- 它应当更接近底层 API，还是更接近上层渲染器
- 如何在保持后端替换可能性的同时，不引入不可审计的中间层成本

---

## 决策

Kadath 采用 **中等粒度 RHI**，其抽象边界以 **Vulkan 风格的资源、命令录制和显式同步模型** 为基础，只对命名、模块边界与后端替换点做统一，不在 RHI 层吸收 `2D` 渲染策略、材质系统或场景级渲染流程。

具体决策如下：

1. **RHI 采用中等抽象，而非极薄封装或高层渲染框架**
2. **先确定抽象边界，再只实现一个真实后端进行验证**
3. **首个验证后端选择 Vulkan**
4. **同步采用最小抽象**
5. **命令模型采用接近 Vulkan 的录制与提交模型**
6. **RHI 层必须对性能开销可测、可控、可审计**

---

## 1. 为什么选择中等抽象

### 1.1 不选极薄抽象

极薄抽象通常只对底层 API 做最小包装，例如：

- 几乎一一映射底层资源对象
- 上层直接理解大量后端特有概念
- 后端差异主要由 `renderer2d` 或更高层承担

这种方式的优点是实现快、额外开销少，但不适合 Kadath 当前目标：

- `Phase 0` 已明确后续存在扩展性诉求
- `renderer2d` 作为上层应关注绘制策略，而不是后端资源细节
- 若将后端细节直接暴露给上层，会使后续替换点过于分散

### 1.2 不选厚抽象

厚抽象会尝试在 `RHI` 层统一更多高层行为，例如：

- render pass 组织策略
- 常见绘制流程
- 材质绑定模型
- 资源调度与批处理结构

这种方式在多人团队和成熟引擎里可能有价值，但对当前 Kadath 来说代价过高：

- 会把未来不确定的渲染策略过早冻结
- 容易形成“最低公分母 API”
- 会让 `M0-M2` 的实现重心从“打通路径”转移到“维护抽象体系”

### 1.3 中等抽象的取舍

中等抽象意味着：

- `RHI` 负责统一基础 GPU 资源、管线与命令提交模型
- `renderer2d` 负责组织上层绘制逻辑、批处理和具体渲染策略
- 后端差异由 `RHI` 承担，但高层渲染语义不进入 `RHI`

这能在“可扩展”与“不过度设计”之间取得平衡。

---

## 2. 首个后端与验证策略

### 2.1 先定抽象，再只实现一个后端

Kadath 不采用“先写一个后端，后面再抽象”的方式，也不采用“一开始就同时实现多个后端”的方式。

采用的策略是：

- 先定义中等粒度的 RHI 边界
- 当前只实现一个真实后端
- 用这个后端验证抽象是否过厚、过薄或不稳定

这样做的理由：

- 能避免抽象完全被某个文件内联实现主导
- 也能避免为了“验证通用性”过早维护多个后端

### 2.2 首个后端选择 Vulkan

首个验证后端定为 `Vulkan`。

原因：

- `Vulkan` 的资源、命令缓冲、队列提交和同步模型足够显式
- 它更容易暴露抽象层是否隐藏了不该隐藏的成本
- 若 `RHI` 能在 Vulkan 上保持边界清晰且无明显冗余，那么后续支持其他显式 API 时更有基础

该决策不意味着 Kadath 承诺近期支持多后端，只意味着：

- 首个抽象验证对象是 `Vulkan`
- 后续是否引入第二后端，将在未来阶段按需求再决策

---

## 3. RHI 负责什么

Kadath 的 `RHI` 层负责以下对象与行为的抽象：

### 3.1 设备与交换链

- `Device`
- `Adapter / PhysicalDevice`
- `Swapchain`
- 与平台窗口句柄对接所需的最小桥接逻辑

### 3.2 基础资源对象

- `Buffer`
- `Texture`
- `Sampler`
- `ShaderModule`
- `PipelineState` 或等价对象
- `Descriptor / Binding Layout` 或等价资源绑定对象

### 3.3 命令录制与提交

- `CommandBuffer`
- `CommandEncoder` 或等价录制上下文
- `Queue`
- 提交批次与最小同步对象

### 3.4 必要同步原语

- `Fence`
- `Semaphore`
- 资源状态转换或 barrier 的显式表达

### 3.5 资源创建与销毁边界

- 资源对象的创建、释放、生命周期规则
- CPU 到 GPU 的上传入口
- GPU 可见资源与宿主可写资源的边界

---

## 4. RHI 不负责什么

以下内容明确不属于 `RHI` 层职责：

### 4.1 2D 渲染策略

`RHI` 不负责：

- sprite 批处理
- draw call 合并策略
- 排序规则
- atlas 组织策略
- 文本或 UI 渲染策略

这些属于 `renderer2d` 或更高层模块。

### 4.2 材质系统

`RHI` 不定义：

- 材质语义
- shader 参数语义层
- render feature 或 pass 组合策略

`RHI` 最多只暴露资源绑定能力和管线创建能力。

### 4.3 场景级渲染流程

`RHI` 不承载：

- render graph
- frame graph
- scene traversal
- visibility / culling 流程

### 4.4 高层资源生命周期策略

`RHI` 不负责：

- 资产热重载策略
- 资源缓存淘汰策略
- 资源引用计数模型
- 资源异步加载调度

这些应由资源系统或上层模块承担。

---

## 5. 同步策略

### 5.1 最小同步抽象

Kadath 的 `RHI` 不尝试隐藏同步。

原则是：

- 暴露必要同步原语
- 允许上层明确感知资源状态变化与提交边界
- 不在中间层自动注入“看不见的同步修复”

### 5.2 为什么不做厚同步包装

若由 `RHI` 自动处理大部分同步：

- 上层将失去对成本的感知
- 调试 GPU 卡顿和 barrier 问题时，归因困难
- 容易引入“为了安全而保守”的隐式同步，导致性能损失

因此，Kadath 选择：

- **同步责任尽量显式**
- **同步成本尽量可见**
- **同步策略尽量不藏在中间层**

---

## 6. 命令模型

### 6.1 接近 Vulkan 的录制与提交模型

Kadath 的 `RHI` 命令模型应尽量接近 Vulkan，包括但不限于：

- 明确的命令录制阶段
- 明确的提交阶段
- 明确的资源状态与同步点
- 明确的队列/执行边界

### 6.2 为什么不做更高层提交接口

若 `RHI` 提供过高层的“自动提交”接口：

- 上层对录制粒度和同步责任的理解会被弱化
- 性能问题更难追踪
- 后续抽象可能被迫吸收更多调度逻辑

Kadath 当前不追求“最少代码调用次数”，而追求：

- 边界清晰
- 行为可解释
- 后端行为可映射
- 性能成本可审计

---

## 7. 性能约束

这是本 ADR 的附加硬约束：**RHI 抽象引入的额外成本必须可测、可控、可审计。**

### 7.1 不允许的隐藏成本

`RHI` 默认不应引入以下隐藏开销，除非文档显式说明：

- 隐式堆分配
- 隐式资源复制
- 隐式提交或隐式 flush
- 隐式同步或保守 barrier 注入
- 无法追踪的状态缓存修正逻辑

### 7.2 可观测性要求

后续实现应能回答这些问题：

- 一个 `RHI` 调用最终映射成哪些 Vulkan 调用
- 一次资源创建是否额外产生了中间对象
- 一次提交是否引入了额外同步原语
- 某个性能回退是来自后端本身，还是来自 `RHI` 包装层

### 7.3 验证方法

虽然本 ADR 不定义具体 benchmark，但后续实现应至少预留：

- `RHI` 调用计数与后端调用计数的对照能力
- 资源创建/销毁路径的日志或统计钩子
- 提交与同步路径的调试开关

---

## 8. 后果

### 正面影响

- `renderer2d` 不会被底层 API 直接绑死
- 后端差异集中在 `RHI` 层，而不是散落到多个高层模块
- 由于首个后端选择 Vulkan，抽象设计会更早暴露真实性能和同步问题
- 中等抽象使 Kadath 在未来具备支持第二后端的可能性，但当前不承担多后端维护成本

### 负面影响

- 仍然需要花时间设计对象模型和命令边界
- 中间层即使控制得当，也会带来一定认知成本
- 若后续纪律不严，`RHI` 容易继续膨胀并吸收高层渲染策略

### 约束性结论

- 后续任何试图把材质系统、2D 批处理、render graph 下沉进 `RHI` 的设计，都应视为偏离本 ADR，需要单独复审
- 后续任何试图把同步“自动处理到看不见”的实现，也应视为偏离本 ADR，需要单独复审

## 9. 相关决策

- **ADR-0001: 语言选型策略** — RHI 作为首期底层图形抽象，依赖 Zig 负责底层系统与 C ABI 边界的语言分工
- **ADR-0002: 构建系统与项目结构** — RHI 模块的目录组织、顶层编排与 `abi/` 契约层约束由本决策承接
- **ADR-0003: 跨语言边界规范** — 若 RHI 向 Rust 侧暴露能力，其 ABI、句柄、错误码与线程语义必须遵守本决策
- **ADR-0005: 世界模型方向** — 世界更新与渲染协作不会改变 RHI 的职责边界；高层世界/渲染策略不得反向下沉进 RHI

---

## 10. 一句话结论

Kadath 的 `RHI` 采用 **以 Vulkan 风格资源、命令录制和显式同步模型为基础的中等抽象**；它统一底层 GPU 对象与提交边界，但不承担高层渲染策略，并要求所有中间层成本可审计。
