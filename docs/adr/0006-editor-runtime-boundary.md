# ADR-0006: 编辑器与 Runtime 边界

## 元信息

- **状态**: 已采纳
- **日期**: 2026-06-03
- **决策者**: @alloyzer0
- **相关主题**: Phase 1 第二轮核心架构议题：编辑器与 Runtime 边界
- **依赖**:

  - `ADR-0004`: RHI 抽象粒度
  - `ADR-0005`: 世界模型方向

## 背景

`Phase 0` 已将“编辑器与 Runtime 的通信边界”识别为中风险议题。它之所以需要在 `Phase 1` 提前处理，不是因为当前马上要实现完整编辑器，而是因为：

- `M0-M2` 的主路径会先落地平台抽象、窗口系统、主循环、渲染器和世界模型
- 若这些基础层把“独立运行的游戏进程”写死为唯一形态，`M4` 再接编辑器时很可能需要拆主循环、改窗口所有权、重做数据边界
- 若当前反过来为了未来编辑器过早实现复杂 IPC、多进程同步或嵌入宿主视图，又会把单人项目拖入过度工程化

因此，本 ADR 需要回答的不是“今天就做哪种编辑器”，而是：

- Kadath 首选的编辑器 / Runtime 关系是什么
- 当前阶段必须预留哪些边界
- 当前阶段明确不预留哪些重量级机制
- 后续 editor、runtime、world、renderer、resource 之间什么可以共享，什么不能共享

结合当前项目事实：

- 首要目标仍是 `2D 俯视角 / PC / 单人开发闭环`
- `M0-M2` 先做出可运行的 Runtime 与可玩 demo
- 编辑器核心、脚本与热重载属于 `M4`
- `ADR-0005` 已确认世界模型不能把内部存储布局暴露给后续系统作为硬依赖
- `ADR-0004` 已确认 `RHI` 只负责 GPU 资源、命令与同步，不吸收高层编辑器职责

这些事实意味着：

- Runtime 纯度仍然优先
- 但 Runtime 不能被实现成一个只能“自启、自跑、自管窗口、自管全局状态”的不可宿主黑盒
- Editor 与 Runtime 的边界应优先围绕生命周期控制和可序列化数据建立，而不是围绕共享内存对象或 UI 嵌入细节建立

---

## 决策

Kadath 采用 **“逻辑分离优先、协议边界收窄、物理集成方式延后”** 的编辑器 / Runtime 边界策略。

具体决策如下：

1. **Editor 与 Runtime 在架构上视为两个独立容器，而不是一个默认同进程的一体化应用**
2. **`M0-M2` 只要求实现独立运行的 Runtime，不要求实现 Editor 或完整 IPC**
3. **Editor 与 Runtime 的首要边界是可序列化数据与粗粒度控制命令，而不是共享内部对象**
4. **Runtime 主循环必须可被拆分为受控生命周期阶段，不能只有一个不可中断的“自旋到底”黑盒循环**
5. **平台层与窗口系统当前可以只实现自有顶层窗口，但实现方式不得排除未来“宿主窗口 / 外部视图”接入**
6. **Editor 专属状态不得下沉进 Runtime 核心模块；Runtime 核心模块也不得把内部状态结构暴露成 Editor 的协议**
7. **当前阶段不锁定具体 IPC 技术、多进程模型、热重载策略或编辑器 UI 形态**

---

## 1. 容器边界

### 1.1 为什么不以内嵌式编辑器作为首选架构

“把编辑器直接做进 Runtime 进程里”在早期实现上很诱人，例如：

- 直接在同一窗口里挂 `imgui`
- 不需要跨进程通信
- 所有对象都能直接拿引用

但 Kadath 当前不把它作为首选架构，原因在于：

- Editor 状态和 Runtime 状态会深度耦合
- 一旦后续需要独立预览、独立资源工具或外部宿主，就会发现当前边界几乎不存在
- “先嵌进去以后再拆开”的成本通常高于“先留边界再逐步接近”
- 当前项目明确把编辑器放在 `M4`，而不是 `M0-M2` 的主线

因此，Kadath 不把“内嵌式单进程编辑器”作为主架构基线。

### 1.2 为什么也不在当前阶段锁死复杂多进程方案

反过来，Kadath 当前也不把“复杂多进程 + 双向高频同步 + 完整宿主窗口嵌入协议”作为立即实现目标。

原因：

- 当前没有编辑器成品要接
- `M0-M2` 不需要为此承担复杂 IPC 负担
- 单人项目在主路径未打通前，不适合先做高复杂度集成基础设施

因此，Kadath 的当前选择不是“马上实现完整分离式编辑器”，而是：

- **先把 Runtime 做成可独立运行的清晰容器**
- **把未来 Editor 接入所需的边界预留清楚**
- **把物理集成方式延后到更接近 `M4` 时再定具体技术**

### 1.3 当前结论

Kadath 对 Editor 与 Runtime 的基线理解是：

- Runtime 是可独立运行、可启动、可停止、可驱动帧推进的运行容器
- Editor 是未来独立存在的工具容器
- 两者之间的稳定契约优先建立在数据与控制边界上，而不是对象地址、进程内引用或 UI 组件拼接上

---

## 2. 生命周期与主循环边界

### 2.1 不允许只有“黑盒大循环”

Runtime 不得只提供一种难以被外部控制的主循环形态，例如：

- `run_forever()` 之后再无外部介入点
- 平台消息、世界更新、渲染提交、资源轮询全都写死在一个不可拆分的大 while 循环中

这样会直接抬高后续 editor 接入成本。

### 2.2 Runtime 必须保留的生命周期阶段

虽然本 ADR 不锁定最终 API 形状，但 Runtime 至少应能在架构上区分以下阶段：

- 初始化
- 载入初始场景或运行配置
- 单帧推进
- 渲染提交
- 暂停 / 恢复
- 停止与释放

这不等于当前就实现完整的外部控制协议，而是要求后续主循环实现不要把这些阶段压平成不可见的内部细节。

对最终可执行入口（如 `app/main.zig`）的直接推论是：

- 默认可执行入口应被设计为一个极薄的“默认宿主”
- 它负责实例化 Runtime 容器，并显式驱动初始化、逐帧推进与停止流程
- 未来若 Editor 需要接管 Runtime，其本质只是换成另一个“宿主”来驱动同一组生命周期边界，而不是重写 Runtime 内核

### 2.3 Editor 未来需要控制什么

未来 Editor 对 Runtime 最常见的控制诉求大致包括：

- 启动预览
- 停止预览
- 暂停 / 恢复
- 请求重新加载场景或配置
- 在某些模式下推进单步或固定步长

当前 ADR 的要求是：

- Runtime 的设计不能排除这些控制语义
- 但本 ADR 不锁定具体命令集合、命令载荷或传输格式

### 2.4 与调度 ADR 的边界

本 ADR 不决定：

- `world.update(dt)` 是否是最终公开入口
- update/render/resource poll 的最终顺序
- 固定步长、变步长、插值帧如何分层
- scheduler 如何组织 stage

这些问题属于后续调度 / 执行模型 ADR。

本 ADR 只要求：**后续调度模型不得把 Runtime 做成无法被外部生命周期控制的封闭黑盒。**

## 3. 平台、窗口与视口边界

### 3.1 当前实现可以只支持自有窗口

在 `M0-M2`，Kadath 当前只要求 Runtime 能创建并管理自己的顶层窗口。

这意味着：

- 平台层当前不必立即支持“采用外部 native window handle”
- 当前不要求实现“把 Runtime 视口嵌入 Editor 宿主窗口”的能力

这能降低当前主路径复杂度。

### 3.2 但实现方式不得把未来宿主模式彻底堵死

虽然当前不要求外部窗口句柄接入，平台层与渲染初始化的实现仍应避免以下写死方式：

- 把窗口创建硬编码成 Runtime 内某个不可替换的全局单例
- 把渲染 surface 创建流程与“必须自己创建窗口”永久绑死
- 把平台消息泵、窗口所有权和帧循环混成不可分离的逻辑块

更合理的方向是：

- Runtime 依赖平台层提供的“窗口 / surface 来源”
- 当前来源可以只有“自有窗口”
- 未来若要支持“宿主窗口”或“外部视图”，应主要扩展平台层能力，而不是重写整个 Runtime 渲染路径

### 3.3 RHI 不感知 Editor

按 `ADR-0004`，`RHI` 只处理设备、交换链、资源、命令与同步。

因此：

- `RHI` 不引入 editor-specific API
- `RHI` 不处理 inspector、视口布局、dock、工具栏等编辑器职责
- 未来即使支持宿主窗口，`RHI` 看到的也应只是平台层提供的 surface / handle 桥接，而不是“编辑器容器语义”

## 4. 数据与协议边界

### 4.1 Editor 与 Runtime 的稳定契约应建立在可序列化数据上

Editor 与 Runtime 的核心边界优先围绕以下类别建立：

- 场景数据
- prefab / 实体模板数据
- 构建后的资源引用与加载配置
- 运行配置
- 预览或调试控制命令

也就是说，Editor 与 Runtime 之间最稳定的共享物应是：

- **可序列化的内容**
- **可解释的控制命令**

而不是：

- 进程内裸对象引用
- 世界内部组件池地址
- renderer 内部缓存对象
- 原始资产（Asset）的编辑期上下文
- 资源系统的临时实现细节

### 4.2 Runtime 不向 Editor 暴露内部存储布局

结合 `ADR-0005`，以下内容不得成为 Editor 协议的一部分：

- `World` 内部对象地址
- ECS 存储结构
- `EntityId` 的实现细节以外的内部定位机制
- renderer 或 collision 的内部缓存结构

Editor 若需要查看或修改 Runtime 数据，应通过：

- 受控查询接口
- 序列化快照
- 显式命令
- 或未来专门定义的调试 / 反射边界

### 4.3 首期不要求高频双向同步协议

本 ADR 不要求当前就支持：

- 高频增量 diff 同步
- 共享内存镜像世界
- 多线程双向实时属性编辑
- 复杂订阅推送协议

这些都属于未来更重的编辑器与工具链议题。

当前锁定的原则只有一条：

**Editor 与 Runtime 的边界优先是粗粒度、可解释、可替换的。**

---

## 5. 状态归属边界

### 5.1 Runtime 负责的状态

Runtime 负责：

- 世界运行状态
- 模拟与更新状态
- 渲染提交状态
- 资源实例化后的运行期状态
- 音频播放与输入采样等运行期职责

### 5.2 Editor 负责的状态

Editor 负责：

- 面板布局
- 选择集
- 检视器展开状态
- 工具模式
- 资源浏览器、层级树、属性面板等 UI 状态

### 5.3 不允许的混合

Kadath 当前不接受以下设计方向：

- 把 inspector 面板状态塞进 Runtime 世界对象
- 把 editor selection 当成 Runtime 核心逻辑的一部分
- 让 Runtime 为了配合编辑器 UI 而暴露内部可变对象树

允许存在镜像或派生表示，但归属边界必须清楚。

需要单独说明的是，Editor 选中对象后的高亮、辅助线、包围盒或 gizmo 绘制并不推翻这条边界。

更合适的方向是：

- Runtime 提供无状态的 debug draw / overlay 类能力
- Editor 每帧显式提交“当前要高亮什么、画哪些辅助元素”的瞬时命令
- Runtime 负责把这些命令转换为绘制结果，但不把“当前选中了谁”维护为自己的长期业务状态

---

## 6. 当前明确不做的事情

### 6.1 不在本 ADR 中锁定具体 IPC 技术

本 ADR 不决定未来使用：

- Socket
- 管道
- 共享内存
- gRPC
- 自定义二进制协议
- 进程内桥接

这些属于后续实现与工具链决策。

不过，`ADR-0003` 已经为未来可能出现的 FFI 形态提供了基础。如果后续 Editor 采用“同进程加载 Runtime 动态库”或其他基于稳定边界驱动 Runtime 的物理装配方式，现有 `C ABI` 规范可以自然承担这类集成的低层接口契约。

### 6.2 不在本 ADR 中锁定 Editor 是多进程、子进程还是宿主嵌入

本 ADR 只锁定逻辑边界，不锁定最终物理装配方式。

未来可能的形态包括：

- Editor 启动独立 Runtime 预览进程
- Editor 宿主承载 Runtime 视口
- Runtime 独立运行并接受外部控制

哪一种更合适，留待更接近 `M4` 时按实现成本和用户体验再定。

### 6.3 不在本 ADR 中承诺热重载能力

脚本热重载、资源热重载、场景热替换都不是本 ADR 的交付内容。

本 ADR 只要求：

- 当前边界不要让这些能力在未来变成“不重写架构就做不了”

### 6.4 不把 Editor 职责下沉到世界模型、RHI 或资源底层

后续任何为了“先方便做编辑器”而把编辑器专属状态或协议直接塞入：

- `World`
- `RHI`
- `platform`
- `resource loader`

都应视为偏离本 ADR，需要单独复审。

## 7. 后果

### 正面影响

- `M0-M2` 可以继续围绕独立 Runtime 推进，不被完整编辑器实现拖慢
- 后续接入 Editor 时，不需要从“完全没有边界”的状态开始硬拆
- 生命周期控制、平台窗口、数据协议会更早拥有清晰分层
- 与 `ADR-0005` 一起，能把“编辑器直接依赖世界内部结构”的风险提前压住

### 负面影响

- 当前不会立即得到一个最低成本的内嵌编辑器原型
- 需要在主循环和平台层实现时保持额外纪律
- 因为暂不锁物理集成方式，未来仍需要一次更具体的编辑器集成决策

### 约束性结论

- 后续任何把 Runtime 实现成不可外控的黑盒大循环的方案，都应视为偏离本 ADR，需要单独复审
- 后续任何把 Editor 协议建立在世界内部对象布局、renderer 内部缓存或进程内裸引用上的方案，都应视为偏离本 ADR，需要单独复审
- 后续任何为了编辑器便利而把 editor-specific 语义下沉到 `RHI` 或底层平台抽象的方案，都应视为偏离本 ADR，需要单独复审

## 8. 相关决策

- **ADR-0001: 语言选型策略** — 平台层与底层窗口 / 设备桥接优先由 Zig 侧承担，Runtime 高层控制与世界交互主要由 Rust API 承接
- **ADR-0002: 构建系统与项目结构** — Editor、Runtime、未来工具容器的目录与顶层编排方式受本决策影响
- **ADR-0003: 跨语言边界规范** — 若未来 editor/runtime 控制接口跨越 Zig / Rust 边界，其 ABI、错误码和线程语义必须遵守本决策
- **ADR-0004: RHI 抽象粒度** — Editor 接入不得改变 RHI 只负责 GPU 资源、命令与同步的职责边界
- **ADR-0005: 世界模型方向** — Editor 不得依赖世界内部存储布局，Runtime 数据访问必须继续经过受控边界

---

## 9. 一句话结论

Kadath 的 Editor 与 Runtime 采用 **“逻辑分离优先、协议边界收窄、物理集成方式延后”** 的策略：当前先把 Runtime 做成可独立运行且可被未来外部控制的容器，同时用可序列化数据与生命周期边界为后续 Editor 接入预留空间。
