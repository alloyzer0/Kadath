# ADR-0007: 资源加载与资产边界

## 元信息

- **状态**: 已采纳
- **日期**: 2026-06-03
- **决策者**: @alloyzer0
- **相关主题**: Phase 1 第二轮核心架构议题：资源加载与资产边界
- **依赖**:
  - `ADR-0001`: 语言选型策略
  - `ADR-0002`: 构建系统与项目结构
  - `ADR-0003`: 跨语言边界规范
  - `ADR-0004`: RHI 抽象粒度
  - `ADR-0005`: 世界模型方向
  - `ADR-0006`: 编辑器与 Runtime 边界

---

## 背景

`Phase 0` 已将“资产管线不透明：黑盒处理、缓存失效不可预测”列为主选痛点 `P2`，同时在里程碑上又要求：

- `M2` 必须先做出可玩 demo，此时 Runtime 已经需要能加载资源
- `M3` 必须能把 demo 打包分发到未安装开发环境的机器上
- `M4` 才进入完整的编辑器闭环、脚本与热重载阶段

这导致资源系统天然横跨两个不同重量级的阶段：

- **前期需要“能读、能跑、能分发”**
- **后期需要“可导入、可转换、可追踪、可编辑、可热重载”**

如果在 `M3` 之前就把完整资产管线塞进 Runtime：

- 会把主路径拖入过度工程化
- 会让平台层、世界模型、渲染器被编辑器和导入工具反向绑架
- 会把原本属于工具链的复杂度灌进运行时核心

如果反过来完全不定义边界，只是先“能读文件就算了”：

- `M3` 的打包方案可能直接变成 Runtime 的永久 API
- `M4` 引入导入、依赖追踪、序列化与热重载时，会发现运行时契约过于贴近物理文件布局
- `P2` 中“黑盒管线”和“缓存不可解释”的痛点会被推迟而不是被约束

因此，本 ADR 需要回答的不是“今天就实现哪种资产管线”，而是：

- `M3` 的极简资源打包到底负责到哪里
- Runtime 的资源加载器应依赖什么样的输入契约
- 哪些事情属于未来完整资产管线
- 哪些复杂能力当前明确不进入 Runtime 核心

结合当前项目事实：

- `ADR-0004` 已确认 `RHI` 不负责资源热重载、高层生命周期策略和资产缓存淘汰
- `ADR-0005` 已确认世界模型不应把内部布局暴露成后续系统硬依赖
- `ADR-0006` 已确认 Editor / Runtime 的稳定边界优先围绕可序列化数据与粗粒度协议建立
- `Phase 0` 明确 `task scheduler` 从 `M3` 起才因异步加载等需求变得必要

这些事实意味着：

- Runtime 需要一个可持续的“资源读取与实例化”边界
- 但完整导入、编译、依赖图、缓存、编辑器协作不应提前下沉进 Runtime
- `M2/M3` 可以为效率允许直接加载少量开发期格式，但这种便利不应被写成长期不可替换的架构承诺

---

## 决策

Kadath 采用 **“Runtime 只负责运行时资源读取与实例化，完整资产管线留在 Runtime 外部并后置到 `M4` 附近”** 的资源边界策略。

具体决策如下：

1. **资源系统拆分为三层概念：源资产、运行时资源、资产管线产物**
2. **Runtime 资源加载器的稳定输入契约应面向逻辑资源标识与字节流 / 资源源抽象，而不是某个固定物理打包格式**
3. **`M2` 允许直接从松散文件加载少量开发期资产格式，但这只是阶段性实现便利，不构成长期格式承诺**
4. **`M3` 只锁定极简资源打包与只读加载边界，不引入完整导入、编译、依赖追踪与编辑器序列化体系**
5. **完整资产管线的职责包括导入、转换、烘焙、依赖分析、缓存管理与编辑器协作，且它在架构上属于 Runtime 外部工具链**
6. **`platform` / `RHI` / `world` 只消费资源系统提供的稳定边界，不直接承担资产导入和构建职责**
7. **当前阶段不锁定最终 archive 格式、热重载协议、缓存键策略或完整 importer/baker 体系**

## 1. 资源层次划分

### 1.1 源资产（Source Assets）

源资产指开发者直接编辑和维护的原始内容，例如：

- `png`
- `wav`
- `tmx`
- `json`
- `glTF` 或未来其他建模资源

这些格式服务于：

- 人工创作
- 外部 DCC / 关卡工具
- 编辑器工作流
- 导入和转换

Kadath 不把“源资产格式”直接等同于“Runtime 长期稳定加载格式”。

### 1.2 运行时资源（Runtime Resources）

运行时资源指 Runtime 在游戏运行中真正消耗的对象或字节内容，例如：

- 纹理像素数据
- 音频缓冲
- tilemap 数据
- shader 字节码或源码
- 场景 / prefab 的运行时表示

这些资源最终会被：

- `renderer`
- `audio`
- `world`
- `script runtime`（未来）

所消费。

Runtime 的稳定职责是：

- 找到这些资源
- 读取其字节内容
- 解析或实例化为运行期对象

### 1.3 资产管线产物（Pipeline Outputs）

资产管线产物指源资产经过导入、转换、烘焙后产生的中间或最终结果，例如：

- 中间描述文件
- 依赖图与缓存记录
- 平台相关压缩纹理
- 适合打包分发的运行时文件

这些产物属于工具链和构建流程关注的对象，不应默认要求 Runtime 理解它们全部的内部生成过程。

## 2. Runtime 资源加载边界

### 2.1 Runtime 以逻辑资源标识请求资源

高层模块不应长期直接依赖：

- 操作系统绝对路径
- 某个具体 zip / archive 内部路径字符串
- 编辑器临时缓存目录

更稳定的方向是：

- 高层通过逻辑资源标识、规范化相对路径或等价的资源键请求资源
- 资源系统负责把它解析到当前激活的资源源

本 ADR 不锁定最终命名形式是 `ResourceId`、逻辑路径还是哈希键，但锁定以下原则：

- **高层请求的是“资源身份”，而不是“当前物理存放位置”**

另外，资源系统需要对“同一逻辑标识在当前运行上下文中代表什么”给出稳定语义。对于纹理、音频、shader、共享 tilemap 等共享型运行时资源，默认应避免同一逻辑标识被重复加载成多份彼此无关的底层驻留实例；若某类资源确实需要多份独立实例，必须由更高层显式建模，而不是把重复加载当成隐式常态。

### 2.2 Runtime 依赖资源源 / 字节流抽象，而不是物理打包格式

资源加载器的稳定输入边界应尽量接近：

- 文件流
- 内存流
- 只读字节块
- 或“给我某个逻辑资源键对应的数据流”的资源源接口

而不是：

- “必须从 zip 读取”
- “必须从自定义 `.kpack` 读取”
- “必须从编辑器缓存目录读取”

这条边界的意义在于：

- `M2` 可从松散文件读取
- `M3` 可从最小 archive / 包文件读取
- `M4+` 可从资产管线产物读取

只要资源系统给上层提供的仍是同一类读取契约，高层模块就不需要跟着物理承载方式反复改动。

### 2.3 `M2` 允许开发期直读，但不形成长期承诺

为保证 `M2` 可玩 demo 的推进速度，Kadath 当前允许：

- 从开发目录直接读取松散资源文件
- 直接解析少量基础格式，如 `png`、`wav`、简单场景描述或 tilemap

但这条允许是**阶段性的工程便利**，而不是长期架构承诺。

约束如下：

- 这种直读能力应尽量收敛在资源系统或其格式 loader 中
- 不得让 renderer、audio、world 直接自行读取 OS 文件
- 不得让上层模块把“资源一定是磁盘上的某个原始 png”当成长期不变前提
- 解析或转换逻辑应隔离在资源加载器前端；运行时纹理、音频缓冲或其他资源对象本身不应携带源格式专用结构或头文件依赖

### 2.4 Runtime 不承担离线式导入 / 烘焙职责

Runtime 不应把以下操作作为常规加载路径的一部分：

- 重型格式转换
- 离线纹理压缩
- 大规模依赖分析
- 编辑器级元数据生成
- 资产缓存数据库维护

如果后续确实需要开发期便利能力，也应被视为：

- 临时开发模式能力
- 或外部工具链能力

而不是 Runtime 的核心职责。

## 3. `M3` 极简打包边界

### 3.1 `M3` 的目标是什么

`M3` 的目标是：

- 让 `M2` 的可玩 demo 可以被分发
- 在未安装开发环境的 PC 上运行
- 降低资源文件散落和缺失的风险

`M3` 的目标不是：

- 建完整内容构建系统
- 解完所有导入格式问题
- 把编辑器所需的资产元数据体系一次做完

### 3.2 `M3` 可以包含什么

`M3` 阶段允许的资源打包能力包括：

- 把松散资源整理为只读目录结构或 archive
- 提供基础 manifest 或索引
- 为 Runtime 提供统一的资源源入口
- 必要时做轻量压缩或简单校验

这些能力的共同特征是：

- 面向**分发**
- 面向**只读消费**
- 不要求 Runtime 知道完整导入历史

### 3.3 `M3` 明确不包含什么

`M3` 默认不包含：

- 完整 importer / baker 管线
- 细粒度依赖追踪图
- 编辑器序列化协议
- 资产数据库
- 复杂缓存失效策略
- 完整热重载体系
- 面向多平台的大规模 cook 产物矩阵

这条约束是为了防止 `M3` 变成“披着打包名义的半套资产平台”。

### 3.4 `M3` 不锁定最终打包格式

当前 ADR 不要求 `M3` 立刻拍板：

- 自定义 `.kpack`
- zip
- 多文件目录 + manifest
- 其他 archive 容器

但要求无论采用哪种物理形式，都应满足：

- 对 Runtime 暴露为统一的只读资源源
- 不让高层模块依赖 archive 内部布局细节
- 后续更换物理格式时，主要影响资源访问层，而不是 renderer / world / audio

## 4. 完整资产管线边界

### 4.1 完整资产管线属于 Runtime 外部工具链

完整资产管线在架构上应视为：

- 未来 `Asset Tool`
- Editor 的配套工具能力
- 构建与内容生产工具链

而不是 Runtime 核心模块的一部分。

这与 `ADR-0006` 中“Editor 与 Runtime 逻辑分离优先”的方向一致。

### 4.2 完整资产管线负责什么

完整资产管线未来负责：

- 导入原始资产
- 格式转换与规范化
- 平台相关烘焙
- 依赖分析与缓存键生成
- 构建产物管理
- 编辑器可见的资产元数据
- 与热重载、预览和内容回写相关的外围流程

这些职责当前不应下沉进 Runtime。

### 4.3 Runtime 与资产管线如何衔接

Runtime 与完整资产管线之间更合适的衔接方式是：

- 资产管线产出 Runtime 可消费的资源文件或包
- Runtime 通过稳定的资源源 / 资源加载边界读取这些产物
- Editor 或工具链决定何时重新导入、重新构建、重新打包

Runtime 不负责回答：

- 某个 png 是由哪个 PSD 导出的
- 某个缓存为什么失效
- 某个 glTF 导入时用了哪套优化规则

这些应由资产管线和工具层承担。

## 5. 模块职责边界

### 5.1 `platform` 只提供 I/O 能力，不提供资产语义

`platform` 负责：

- 文件读取
- 目录遍历
- 时间戳、路径与基础 I/O 能力

`platform` 不负责：

- 判断某个 png 如何导入
- 维护资产依赖图
- 解释编辑器缓存目录结构

如果资源系统需要跨越 Zig / Rust 边界传递大块文件数据，也必须继续遵守 `ADR-0003` 的内存分配模式与释放规则，避免在 `C ABI` 边界上形成“谁分配、谁释放”不清楚的大块缓冲区泄漏。

### 5.2 `RHI` 不接管资产导入

按 `ADR-0004`，`RHI` 只处理 GPU 资源、命令和同步。

因此：

- `RHI` 不承担纹理导入规则
- `RHI` 不承担 shader 资产管理策略
- `RHI` 不承担热重载缓存与编辑器资源协议

`RHI` 最多只接收资源系统已经准备好的运行时输入。

### 5.3 `world` 与高层模块保存资源身份，而不是物理来源

按 `ADR-0005`，世界模型与高层逻辑应尽量依赖稳定语义边界。

因此更合理的方向是：

- 场景、prefab、组件保存逻辑资源引用
- 资源系统负责解析这些引用
- 高层模块不把“资产位于某个绝对路径 / 某个 archive 偏移”写进公开语义

### 5.4 `scheduler` 在 `M3+` 只解决异步读取，不等于完整管线调度

`task scheduler` 在 `M3+` 可以承担：

- 异步文件读取
- 后台解码
- 资源上传前准备

但它当前不等于：

- 资产导入 DAG 执行器
- 完整内容构建系统
- 编辑器增量重建框架

## 6. 当前明确不做的事情

### 6.1 不在本 ADR 中锁定最终资源包格式

本 ADR 不决定最终是否使用：

- `.kpack`
- zip
- 多目录布局
- 其他自定义容器

### 6.2 不在本 ADR 中锁定资源标识的最终编码形式

本 ADR 只锁定“逻辑资源身份优先于物理位置”，不锁定最终采用：

- 字符串路径
- 规范化相对路径
- 数值 `ResourceId`
- 哈希键

### 6.3 不在本 ADR 中承诺完整热重载

本 ADR 不承诺：

- 改资源立即热替换
- 依赖级联自动重建
- 编辑器内实时材质 / 纹理回刷

当前只要求 Runtime / 资源边界不要把这些未来能力彻底堵死。

### 6.4 不把开发期直读便利升级为永久契约

如果 `M2/M3` 直接读取源资产格式很方便，这可以接受；
但后续若要过渡到完整资产管线，不应因此被迫保持：

- “Runtime 永远直接吃原始 png / wav / tmx”
- “所有分发包都必须保留开发期原始格式”
- “上层模块永远知道资源来自松散文件”

### 6.5 不在本 ADR 中锁定完整 importer / baker 体系

本 ADR 不决定：

- 中间格式是否叫 `.kasset`
- 是否需要统一 importer 插件 API
- bake 阶段的缓存数据库结构
- 多平台 cook 产物目录布局

这些属于未来更靠近工具链实现的议题。

## 7. 后果

### 正面影响

- `M2` 与 `M3` 可以先围绕“能加载、能打包、能分发”推进，而不必先背上完整资产平台
- Runtime 的资源边界会更稳定，不容易被某一代物理打包格式绑死
- 后续 editor、asset tool、hot reload 的复杂度能被留在工具链侧，而不是灌进核心运行时
- 与 `ADR-0006` 配合后，Editor / Runtime / Asset Tool 三者的分层会更清楚
- 为未来 3D / HD-2D 或更复杂内容格式保留了扩展空间

### 负面影响

- `M2/M3` 早期可能存在“开发期直读”和“分发期打包”两套较轻的资源入口
- 当前不会立即解决 `P2` 中所有“资产管线透明度”问题
- 未来真正实现完整资产管线时，仍需要一次更具体的工具链 ADR 或设计文档

### 约束性结论

- 后续任何把完整 importer / baker、依赖图和编辑器序列化直接塞进 Runtime 核心的方案，都应视为偏离本 ADR，需要单独复审
- 后续任何让高层模块长期依赖绝对路径、archive 内部布局或开发期源文件位置的方案，都应视为偏离本 ADR，需要单独复审
- 后续任何让 `RHI`、`world` 或 `platform` 直接承担资产导入语义的方案，都应视为偏离本 ADR，需要单独复审

## 8. 相关决策

- **ADR-0001: 语言选型策略** — 资源读取底层与平台 I/O 优先由 Zig 侧承接，高层资源语义和使用场景会更多落在 Rust 与上层模块
- **ADR-0002: 构建系统与项目结构** — Runtime 资源模块、未来工具模块与打包流程的目录和顶层编排受本决策影响
- **ADR-0003: 跨语言边界规范** — 若资源系统跨越 Zig / Rust 暴露 ABI，其流式读取、内存所有权与错误码必须遵守本决策
- **ADR-0004: RHI 抽象粒度** — 资源系统不得把高层资产导入或热重载策略错误地下沉到 `RHI`
- **ADR-0005: 世界模型方向** — 世界与场景层应保存资源身份而不是资源物理存放细节
- **ADR-0006: 编辑器与 Runtime 边界** — 完整资产管线属于 Runtime 外部工具链，与 Editor 一样优先通过数据与协议边界衔接

---

## 9. 一句话结论

Kadath 的资源边界采用 **“Runtime 负责运行时资源读取与实例化，完整资产管线留在 Runtime 外部并后置到 `M4` 附近”** 的策略：`M3` 只解决极简打包与只读加载，`M4+` 再引入导入、烘焙、依赖追踪和编辑器协作。
