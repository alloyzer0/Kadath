## 背景

`Phase 0` 已将世界模型识别为高风险架构议题之一。其风险不在于“选 ECS 还是 OOP”这个口号本身，而在于：

- 对开发者公开什么语义
- 内部如何处理热点性能路径
- 是否要为未来另一种范式保留演进空间
- 如何保留边界而不演变成“双系统并存”

结合当前项目事实：

- 首要目标仍是 `2D 俯视角 / PC / 单人开发闭环`
- 上层引擎接口主要由 Rust 定义
- 开发者主要直接调用 Rust API
- 首期既需要自然、稳定、易理解的世界语义
- 也需要为高频批处理和热点数据保留性能优化路径

这些事实进一步意味着：

- 当前首要场景不要求大世界流式加载、网络同步或超大规模实体管理，因此对外语义优先保证直观性与稳定性
- 但 2D 渲染、运动与碰撞路径已足以形成高频批处理与热点数据访问，因此内部不能完全排斥数据导向优化

因此，Kadath 的世界模型不采用“纯 OOP”或“纯 ECS”的单极方案，而采用：

- **对外语义以 OOP / 对象导向为主**
- **内部对热点数据与热点系统允许采用 ECS / 数据导向优化**
- **不对外暴露双套并列范式**
- **保留中等强度的演进边界，但不预先实现双系统**

---

## Phase 1 P4 回答

本 ADR 对 `Phase 1` 准入议题中的 `P4`（避免强制 ECS 或强制 OOP 导致架构模型僵化）的回答是：

- **首期主范式**：对外采用对象/实体导向语义，开发者不需要直接围绕底层 ECS 存储模型编程。
- **内部优化方式**：热点数据与热点系统允许采用 ECS / 数据导向实现，以保留批处理和缓存局部性优化空间。
- **预留强度**：保留身份、访问、调度和数据定义四类中等强度边界，但不承诺首期实现双范式运行时。
- **明确不选**：不选纯 ECS 公开 API、不选纯 OOP 底层实现、不选 OOP 世界与 ECS 世界双核并存。

因此，`P4` 的落地方式不是“同时支持两套完整范式”，而是“对外单一语义入口 + 内部热点路径可演进”。这能回应架构僵化风险，同时避免单人项目在首期承担双系统维护成本。

---

## 0. 决策摘要

Kadath 的世界模型采用 **“对外 OOP 语义为主，内部热点路径允许 ECS/数据导向优化”** 的混合式方案。

具体决策如下：

1. **首期对开发者公开的世界语义采用对象/实体导向接口**
2. **不对外暴露 OOP 与 ECS 两套并列的一等 API**
3. **内部允许对热点数据采用 ECS/数据导向存储**
4. **内部允许对热点系统采用批处理式系统更新**
5. **为未来范式演进保留中等强度边界**
6. **当前不实现双世界模型或双运行时系统**
7. **调度边界只定义原则，不在本 ADR 中锁定具体更新入口 API**

---

## 1. 对外语义

### 1.1 首期公开语义为何不采用纯 ECS

纯 ECS 适合作为性能导向的底层组织方式，但不适合作为 Kadath 当前阶段的首期公开语义，原因在于：

- 当前目标不是先做一个“纯 ECS 引擎”
- 开发者主要通过 Rust API 与世界交互，更需要自然稳定的语义层
- `2D demo` 首期更强调“对象/实体在世界中存在并被操作”的直观表达
- 若首期直接把 ECS 暴露为主要开发心智，会提升使用门槛和工具性成本

### 1.2 首期公开语义为何也不采用纯 OOP

纯 OOP / 场景对象模型虽然更直观，但不足以覆盖后续热点性能需求：

- 热点路径数据容易离散
- 批量更新和局部性优化不友好
- 后续一旦需要做高频系统优化，容易导致底层大改

因此，Kadath 不把纯 OOP 作为底层唯一实现方式，而是将其定义为：

- **首期对外语义**
- 而不是内部实现必须遵守的唯一存储与调度方式

### 1.3 当前结论

首期对外世界接口以对象/实体语义为主。
开发者看到的是：

- 世界中存在实体/对象
- 实体拥有组件或属性
- 世界提供统一的创建、销毁、查询、访问与更新边界

开发者不需要在首期直接围绕 archetype、chunk 或底层 query 模型编程。

---

## 2. 内部热点路径的 ECS 化

### 2.1 原则

Kadath 明确允许在内部对热点路径采用 ECS / 数据导向实现，但仅限于：

- 高频
- 批量
- 数据局部性明显
- 对遍历与缓存友好的路径

这是一种内部实现策略，不等价于对外公开双范式 API。

### 2.2 首期热点数据

首期允许优先采用数据导向存储优化的数据包括：

- `Transform`
- `Velocity / Movement`
- `SpriteInstance / RenderData`
- `CollisionBody / Broadphase 数据`

这些数据的共同特点是：

- 数量较大
- 访问频率高
- 常被系统顺序遍历
- 更容易从连续布局中获益

### 2.3 首期热点系统

首期允许优先采用批处理式系统更新的逻辑包括：

- `MovementSystem`
- `TransformPropagationSystem`
- `SpriteSyncSystem`
- `CollisionBroadphaseSystem`
- `CollisionResolveSystem`

本列表为首期示例，不构成穷举；后续是否适合采用 ECS/数据导向实现，应以 2.1 节中的四条判据为准，而不是以是否出现在本列表中为准。

这些系统的共同特点是：

- 对顺序遍历和批处理更友好
- 对数据局部性敏感
- 若完全按对象逐个分派方法执行，后续优化成本更高

---

## 3. 中等强度的演进边界

Kadath 不在首期同时实现两套完整世界系统，但会在以下四层保留范式演进边界。

### 3.1 身份边界

上层不直接依赖某类具体对象指针作为长期身份。

统一要求：

- 世界中的可持久引用对象通过稳定 `EntityId` 被识别
- 上层逻辑不把底层存储地址视为实体身份

### 3.2 访问边界

上层不默认直接操作底层内部存储。

统一要求：

- 通过世界接口、查询接口、组件访问接口获取和修改数据
- 不把底层对象布局暴露成跨模块约定

### 3.3 调度边界

首期不把“对象自己 tick”写死为唯一更新模型。

统一要求：

- 世界模型必须能被统一调度边界驱动
- 内部可区分对象语义层更新与系统批处理更新
- 上层依赖的是世界调度边界原则，而不是某个具体更新 API
- 本 ADR 不锁定具体更新入口，但后续调度/执行模型 ADR 不得要求上层直接调用对象内部更新方法作为唯一主路径

### 3.4 数据定义边界

热点组件的数据定义应保持独立，不深嵌在继承树语义中。

例如：

- `Transform`
- `Velocity`
- `SpriteInstance`
- `CollisionBody`

这些数据应被视为独立数据单元，可由不同存储策略承载，而不是只能绑定到某个固定对象层级。

### 3.5 周边子系统边界

世界模型可以向渲染、碰撞和调度提供必要的数据入口，但不能把这些子系统变成世界内部存储的直接使用者。

统一要求：

- `RHI` 不感知 `EntityId`、组件、世界对象或场景语义，只处理 GPU 资源、命令和同步。
- `renderer` 可以消费由世界模型或渲染同步层产出的渲染数据，但不直接依赖世界内部存储布局。
- `collision` 可以维护自己的 broadphase、窄相缓存或临时工作集，但实体身份与组件访问仍应回到 `World` 的受控边界。
- `scheduler` 可以驱动世界更新阶段，但不得要求上层对象自行暴露不可替换的 `tick` 链作为唯一执行模型。

这些边界的目的不是提前定义完整数据流 API，而是防止后续实现把世界模型、渲染策略、碰撞缓存和底层 RHI 职责揉成一个难以替换的整体。

## 4. EntityId 设计

### 4.1 对外身份类型

Kadath 对外使用值类型 `EntityId` 作为统一实体身份。

`EntityId` 的职责是：

- 表示“某个实体身份”
- 作为跨系统、跨帧、跨容器传递的稳定引用
- 为未来底层存储演进提供中立身份层

### 4.2 内部实现形式

`EntityId` 内部采用：

- `index + generation`

这种设计的目的在于：

- 支持高效索引
- 检测实体被销毁并复用后的失效引用
- 避免“旧 ID 意外命中新实体”的问题

`EntityId` 的位宽与编码布局暂不在本 ADR 中锁定；该决策留给后续实现/接口 ADR，并须在首个世界模型实现 PR 合入前冻结，以避免影响保存格式、序列化表示和潜在网络传输约定。

### 4.3 生命周期与有效性

`EntityId` 允许长期保存。
例如可被存放于：

- 事件队列
- 引用关系
- 系统缓存
- 脚本层或玩法层对象

但任何实际访问都必须通过 `World` 验证其有效性。

也就是说：

- 持有 `EntityId` 不代表实体当前一定仍然存在
- 任何解引用、查询、修改都必须回到 `World` 做有效性检查

### 4.4 显式无效值

Kadath 提供显式无效值：

- `EntityId::INVALID`

其用途包括：

- 占位
- 默认初始化
- 表达“当前无实体引用”

但它不应被用作“访问失败后静默继续”的默认控制流工具。

### 4.5 `EntityId` 不是活对象引用

`EntityId` 只表示身份，不表示活对象引用。

因此：

- 不允许通过 `EntityId` 直接拿裸内部对象
- 不允许把 `EntityId` 视为底层对象指针的别名
- 访问实体数据必须通过 `World` 的受控接口完成

### 4.6 首个实现前必须冻结的内容

本 ADR 不锁定 `EntityId` 的完整位布局，但首个 `world` 模块实现合入前必须补充或确认以下内容：

- `EntityId` 的位宽、`index` 与 `generation` 的编码方式
- `EntityId::INVALID` 的具体表示
- `EntityId` 在日志、调试输出和潜在序列化中的显示/编码约定
- `World` 对失效 `EntityId` 的访问失败表达方式

这些内容一旦进入公开 API、保存格式或跨语言 ABI，后续修改成本会明显升高，因此不得拖到首个稳定实现之后再补决策。

## 5. 当前明确不做的事情

### 5.1 不实现双世界模型

Kadath 当前不实现：

- 一套完整 OOP 世界
- 一套完整 ECS 世界
- 再由上层自由切换

这样会显著提高维护复杂度，并使 `Phase 1` 失去收敛性。

### 5.2 不对外公开双套并列 API

Kadath 当前不提供：

- 一组对象式 API
- 一组 ECS query/system API
- 让开发者自行选择主入口

否则会导致文档、示例、维护和演进全部分裂。

### 5.3 不在本 ADR 中锁定世界更新入口形式

本 ADR 不决定以下问题：

- `world.update(dt)` 是否是最终入口
- 是否采用 `run_stage(stage, dt)`
- 固定步长与变步长更新如何分层
- 调度系统如何与世界、碰撞、渲染同步协作

这些问题被视为调度/执行模型议题，应在后续专门 ADR 中决定。

### 5.4 不在本 ADR 中锁定保存、脚本与编辑器语义

本 ADR 不决定以下问题：

- 场景或 prefab 的保存格式
- 脚本语言如何绑定世界对象
- 编辑器如何展示、编辑或热重载世界数据
- `EntityId` 是否可跨进程、跨存档或跨网络稳定复用

这些问题会受到资源/资产边界、编辑器边界和脚本运行时设计影响。当前只要求世界模型不要把内部存储布局暴露成这些后续系统必须依赖的协议。

---

## 6. 对 Rust API 的影响

### 6.1 Rust API 保持对象语义友好

由于开发者主要通过 Rust API 使用 Kadath，首期世界接口应优先保证：

- 语义直观
- 生命周期清晰
- API 稳定
- 业务逻辑书写成本低

因此，对外 API 层应更接近：

- 实体/对象句柄
- 组件访问接口
- 世界查询与操作边界

而不是要求开发者直接围绕底层存储策略写业务代码。

### 6.2 内部实现可独立演进

Rust API 不应直接暴露内部热点 ECS 存储细节。

这样未来若：

- 热点数据布局调整
- 组件池改造
- 某个系统从对象式改成批处理式

可以主要在内部完成演进，而不强迫上层 API 同步震荡。

## 7. 后果

### 正面影响

- 对开发者公开的世界语义自然稳定，适合当前 `2D demo` 与单人开发节奏
- 热点路径保留明确的性能优化通道
- 首期不承担双系统并存的复杂度
- 通过中预留边界，为未来更进一步的数据导向演进保留空间

### 负面影响

- 对外语义与内部实现策略不完全一致，需要更强的文档纪律
- 若边界控制不严，可能逐渐演变成“对外对象、对内混乱”的折中系统
- 某些性能优化需要在对象语义层与数据层之间做额外映射

### 约束性结论

- 后续任何试图直接对外暴露双套世界 API 的方案，都应视为偏离本 ADR，需要单独复审
- 后续任何试图把全部逻辑都强制 ECS 化或全部逻辑都退回纯对象式的方案，也应视为偏离本 ADR，需要单独复审
- 后续任何让 renderer、collision、scheduler 或脚本层直接依赖世界内部存储布局的方案，都应视为偏离本 ADR，需要单独复审

## 8. 定稿评审结果

按当前 Phase 1 评审目标，本 ADR 已覆盖以下问题：

- `P4` 的架构回答：不做纯 ECS、纯 OOP 或双世界模型，采用单一对外语义与内部热点优化边界。
- `EntityId` 的公开语义：稳定身份值，不是活对象引用，实际访问必须经由 `World` 验证。
- `World` 访问边界：上层不得依赖底层对象地址、存储布局或内部 ECS 数据结构。
- 调度边界：不把“对象自己 tick”写死为唯一模型，后续调度 ADR 可以在统一边界下继续收束。
- 周边子系统边界：RHI、renderer、collision、scheduler 不直接吸收世界模型内部职责。

本 ADR 仍刻意不锁定以下内容：

- 完整世界更新 API
- `EntityId` 位布局和序列化细节
- 保存格式、脚本绑定、编辑器协议
- 具体 ECS 存储结构、query 语法或系统调度实现

因此，本 ADR 已具备进入主导者审阅的条件；若主导者接受本方向，下一步可进入 `ADR-0006：编辑器与 Runtime 边界` 或先补一份更窄的调度/执行模型 ADR。

## 10. 一句话结论

Kadath 的世界模型采用 **“对外 OOP 语义为主，内部热点路径允许 ECS/数据导向优化”** 的混合方案；首期不实现双系统并存，但在身份、访问、调度原则和组件数据定义层保留中等强度的演进边界。

## 11. 2026-08-21 补充：World 外部语义与内部 authority

本节由 `ADR-0009` 触发，补充当前 Scene、Editor 与 Luau 已经落地后的 World 使用方式；原有“对象/实体导向外部语义 + 内部热点数据导向”的决策继续有效。

### 11.1 当前事实

- 项目开发者主要通过 Scene Authoring、C# Editor 与 Luau `ObjectRef` 使用 World 语义，而不是直接链接 Rust crate；
- Rust `world` 当前拥有 Sprite Entity 存储和基本 fixed-step；
- Zig `SceneGeneration`、`BehaviorHost` 与 `RuntimeObjectRegistry` 当前拥有 ObjectId 映射、phase mutation、动态对象生命周期和 stale 语义；
- 该分布是迁移起点，不是长期双 authority 目标。

### 11.2 目标裁决

- Rust Runtime Core 是 ObjectId、Runtime Entity、generation、source/transient 生命周期和 gameplay state 的唯一内部 authority；
- Scene、Editor 与 Luau 继续消费对象/实体导向语义，但只通过版本化外部 Interface 和 Adapter，不依赖 Rust layout；
- Zig Host 决定 phase 调用时机，Rust Runtime Core 决定 phase 内 World state transition；
- Renderer 只消费 caller-owned snapshot，不反向读取 World 容器；
- 迁移必须在每个增量中删除对应 Zig authority，禁止长期保留 Zig Registry + Rust Registry 双写；
- 是否采用 ECS、稠密组件池或其它数据布局仍是 Rust Runtime Core 的私有 Implementation 决策，不进入 Scene/Luau/Editor Interface。

因此，本文早期“开发者主要通过 Rust API”应按今天的产品形态理解为：**开发者使用的稳定对象语义由 Rust Runtime Core 统一实现和约束，但实际入口可以是 Scene、Luau 或 Editor Adapter。**

## 12. 2026-08-27 补充：Gameplay-neutral Scene

Runtime ownership 迁移完成后，当前 Scene Object Interface 仍要求固定 Demo Gameplay 角色。该要求曾用于尽快交付 M2 Demo，但不应继续成为通用 World / Scene 的有效性前提。

- Scene 必须能在没有 Player、Goal 和 Hazard 的情况下承载 Object、Behavior 与 Render 生命周期；
- Gameplay 是 Scene 显式选择的可选 Module，不得仅由 Object Kind 或对象数量隐式激活；
- 旧 Scene schema 可以由 Adapter 归一化到兼容 Gameplay Profile，但新 Neutral Scene 不伪造角色或 GameSession；
- 本补充不授权公开通用 ECS、archetype 或任意组件集合，仍保持单一对象语义 Interface；
- Gameplay 可选化后的内部存储、候选事务和 render extraction 继续由 Rust Runtime Core 隐藏，Scene、Editor 与 Luau 不依赖其 layout。
