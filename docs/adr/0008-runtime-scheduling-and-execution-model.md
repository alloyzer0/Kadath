## 背景

在 `ADR-0005` 中，世界模型已经明确：

- 不把“对象自己 tick”写死为唯一更新模型
- 世界必须能被统一调度边界驱动
- `world.update(dt)`、`run_stage(stage, dt)`、固定 / 变步长分层等问题留待后续 ADR 决定

在 `ADR-0006` 中，Editor / Runtime 边界又进一步要求：

- Runtime 不能是不可外控的黑盒大循环
- Runtime 必须保留初始化、单帧推进、暂停 / 恢复、停止等生命周期阶段
- Editor 未来需要能够启动预览、暂停、单步推进或重载场景

在 `ADR-0007` 中，资源边界也提出新的约束：

- 异步资源读取和后台准备工作会在 `M3+` 进入主线
- 但这些后台任务不应反向支配 Runtime 的主循环结构

这三个方向叠加后，`Kadath` 现在必须回答一个非常具体的问题：

**Runtime 每一帧到底如何推进？**

如果不在 `Phase 1` 先锁这一层，后续实现很容易出现以下偏差：

- `app/main.zig` 被写成“平台消息 + 世界更新 + 渲染 + 资源轮询”杂糅的单个 while 循环
- 模拟步长随着渲染帧率飘动，碰撞、移动和输入响应行为不稳定
- 异步任务完成回调在任意时点直接改世界，导致边界失控
- Editor 未来想做暂停、单步、预览时，发现主循环没有可插手的阶段

因此，本 ADR 需要锁定的不是某个最终函数签名，而是：

- Runtime 的外层执行形态
- 模拟与渲染之间的时间关系
- 调度阶段的最小结构
- 背景任务如何与主循环同步
- 哪些东西当前明确不做

---

## 决策

Kadath 采用 **“外层变频驱动 + 内层固定步长模拟 + 明确阶段边界 + 受控同步点回流”** 的执行模型。

具体决策如下：

1. **Runtime 的外层宿主循环按平台实际帧节奏推进，但世界模拟采用固定步长**
2. **渲染不驱动世界模拟；渲染消费的是最近一次已提交的模拟状态，以及未来可选的插值信息**
3. **固定步长补偿需要设置单帧最大补偿步次数，以防止“死亡螺旋”**
4. **Runtime 的单帧推进必须拆分为明确阶段，而不是黑盒式一体循环**
5. **世界更新入口由 Runtime 调度边界统一驱动，不要求上层对象逐个暴露 `tick` 作为唯一主路径**
6. **后台任务与异步资源加载只能在受控同步点把结果回流到 Runtime / World**
7. **`task scheduler` 与“执行模型”是两个层次：前者是后台工作机制，后者是主线程上 Runtime 的权威推进顺序**
8. **当前阶段不锁定最终公开 API 名称、完整多线程执行策略、网络确定性或 replay 体系**

## 1. 外层循环与时间模型

### 1.1 外层循环按实际帧节奏推进

Kadath 的默认宿主循环仍然运行在平台驱动的外层帧节奏上。

这意味着每次外层推进通常会做这些事情：

- 采样时间
- 处理平台消息 / 输入
- 累积经过时间
- 运行零次到多次固定步长模拟
- 提取并提交本帧渲染

这与 `ADR-0006` 中“默认宿主只负责驱动 Runtime 容器”的方向一致。

### 1.2 世界模拟采用固定步长

世界模拟默认采用固定步长，例如：

- `1 / 60s`
- 或等价的固定 `dt`

本 ADR 不强制具体数值，但锁定以下原则：

- 同一阶段的世界逻辑、运动、碰撞和主要游戏规则应基于固定步长推进
- 不把渲染帧间隔直接作为世界核心模拟 `dt`

选择固定步长的理由：

- 2D 游戏的运动、碰撞和输入响应更稳定
- 更有利于调试和复现
- 未来若需要 pause / step / replay / editor preview，也更容易控制

### 1.3 渲染允许按变频工作

渲染不需要强制和模拟步长完全同频。

外层每次帧推进时：

- 可能执行 `0` 次模拟步
- 也可能执行 `1` 次或多次补偿模拟步
- 但通常只做一次渲染提取与提交

因此，Kadath 默认采用：

- **固定步长模拟**
- **变频渲染**

而不是“每渲染一帧就做一次等比例世界更新”。

### 1.4 插值是边界预留，不是当前强制交付

未来如果需要更平滑的显示，可以在渲染阶段消费：

- 上一次模拟状态（`prev_state`）
- 当前模拟状态（`curr_state`）
- 插值系数（`alpha = accumulator / fixed_dt`）

但本 ADR 不要求当前就实现完整插值渲染。

当前只锁定：

- 执行模型不能排斥插值边界
- 渲染层不应直接把变动中的世界内部状态当成唯一来源
- 世界模型或渲染同步层不能只保留单一不可回看的状态表示

### 1.5 补偿步次数上限

固定步长模型在低帧率或卡顿时可能出现一帧内需要连续补偿很多次模拟步的情况。

如果不设上限：

- 主线程可能长时间困在补偿循环里
- 渲染越来越追不上模拟
- 最终进入“死亡螺旋”

因此，Kadath 默认要求：

- 单帧固定步长补偿必须设置最大步次数上限
- 当前建议默认值为 **5 次**
- 若累计时间超过本帧可补偿上限，允许丢弃超出的累计时间或做等价的截断处理，以优先恢复交互与显示节奏

本 ADR 锁定的是“必须存在上限”这一原则，不锁死最终常量名或调试配置方式。

## 2. 单帧推进的最小阶段

### 2.1 Runtime 至少应区分的阶段

Runtime 的单帧推进在架构上至少应能区分以下阶段：

1. **平台消息 / 输入采样**
2. **后台结果回流与外部控制命令摄取**
3. **固定步长模拟循环**
4. **渲染提取**
5. **渲染提交**
6. **帧末清理 / 统计**

本 ADR 不要求这些阶段已经都暴露成公开 API，但要求实现时能在结构上看见它们，而不是揉成不可拆分的一整坨。

### 2.2 平台消息 / 输入采样先于模拟

外层每帧应先：

- 处理窗口消息
- 采样输入状态
- 生成当前帧或当前模拟批次可消费的输入快照

这样后续固定步长模拟使用的是：

- **明确时刻采样到的输入**

而不是在模拟过程中随意查询平台实时状态。

### 2.3 后台结果回流与外部控制命令先于模拟

在进入模拟阶段前，Runtime 应有一个受控同步点，用于吸收：

- 资源异步读取完成结果
- 后台任务产物
- Editor 或宿主下发的粗粒度控制命令

这样做的目标是：

- 防止后台线程在任意时点直接改世界
- 让状态变化发生在可解释的边界上

其典型时序可接近：

```text
frame_start()
  sample_input()
  sync_async_results()
  while accumulator >= fixed_dt && steps < max_steps:
    simulate_fixed_step(fixed_dt)
    steps += 1
  extract_render()
  submit_render()
```

当前伪代码只用于表达同步点位置：

- 后台结果在固定步长循环前并入
- 固定步长循环受 `max_steps` 约束
- 渲染提取与提交发生在本轮模拟推进之后

### 2.4 固定步长模拟循环是世界推进主路径

当累计时间超过一个或多个固定步长时，Runtime 执行模拟循环。

每个固定步长中，至少概念上包含：

- 输入快照消费
- 世界主要系统推进
- 碰撞 / 移动 / 游戏逻辑更新
- 必要的事件产出或状态提交

本 ADR 不锁定系统内部的更细 stage 名称，但锁定一点：

- **世界推进的主路径由 Runtime 调度边界驱动，而不是对象自行任意递归更新**

### 2.5 渲染提取与渲染提交分离

渲染阶段至少应概念上拆成两步：

- 从世界 / 渲染同步层提取本帧需要的渲染数据
- 把这些数据提交给 renderer / RHI

这样可以保持：

- world 不直接依赖 RHI
- renderer 不直接支配世界模拟
- 后续做 editor overlay、debug draw 或 render graph 扩展时边界更清楚

## 3. 世界更新入口边界

### 3.1 不把对象逐个 `tick` 写死为唯一模型

按 `ADR-0005`，Kadath 不要求每个对象都暴露：

- `tick(dt)`
- `update(dt)`

作为唯一更新主路径。

更合理的方向是：

- Runtime 驱动世界边界
- 世界边界内部再组织对象语义层更新和系统批处理更新

### 3.2 `world.update(dt)` 可以作为宿主入口候选，但不是本 ADR 唯一承诺

从宿主视角看，未来很可能存在类似：

- `world.update_fixed(dt)`
- `runtime.step_frame(frame_input)`
- `runtime.advance_simulation(dt)`

这样的入口。

本 ADR 不锁定具体函数名，但锁定它们应具备的语义：

- 由 Runtime 或宿主统一调用
- 表示一次受控的模拟推进
- 不要求调用者理解内部 ECS 细节或逐对象调度细节

### 3.3 调度边界服务于 Editor 的 pause / step

因为模拟是固定步长、且由 Runtime 显式驱动，所以未来 Editor 或测试宿主可以自然支持：

- 暂停
- 单步推进一个 fixed tick
- 连续播放
- 重启场景后重新进入推进循环

这正是本 ADR 相对“黑盒大循环”的核心收益之一。

## 4. 背景任务与同步点

### 4.1 执行模型不等于任务系统

本 ADR 所说的“调度 / 执行模型”主要是：

- Runtime 主线程上的权威推进顺序

它不等同于：

- Rust `scheduler` 模块的线程池实现
- 资源系统的后台任务队列
- 编辑器与 Runtime 之间的 IPC 调度

也就是说：

- `scheduler` 是后台工作机制
- Runtime execution model 是主线程状态何时推进、何时提交、何时吸收结果

两者相关，但不是同一层问题。

### 4.2 后台任务结果只能在受控同步点回流

异步资源加载、后台解码、构建结果通知等，不得直接在后台线程上：

- 修改世界
- 修改 renderer 前台状态
- 直接触发高层 gameplay 回调

更合理的方向是：

- 后台任务只产生完成结果或事件
- 主线程在帧开始前或模拟前的同步点统一摄取
- 再由 Runtime 决定何时把这些结果并入运行状态

### 4.3 `M0-M2` 默认单线程主路径

为避免过早复杂化，`M0-M2` 默认可采用：

- 主线程驱动平台、模拟与渲染
- 无后台任务或只有很轻的辅助任务

`M3+` 再逐步引入：

- 异步资源读取
- 后台准备任务
- 更明确的 scheduler 协作

但即使到了 `M3+`，主线程上的 Runtime 推进顺序仍应保持为本 ADR 锁定的权威模型。

## 5. 与周边模块的边界

### 5.1 `platform` 提供消息与时间，不定义世界推进语义

`platform` 负责：

- 窗口消息泵
- 输入采样
- 时钟与时间源

但它不负责：

- 决定世界以什么步长更新
- 决定模拟与渲染如何交织
- 决定后台任务何时回流

### 5.2 `world` 提供受控推进边界，不直接主导宿主循环

`world` 负责承接：

- 一次模拟推进
- 组件 / 系统状态变化
- 事件和数据产出

但它不负责：

- 自己管理平台消息泵
- 自己决定何时渲染
- 自己决定何时吸收资源异步完成结果

### 5.3 `renderer` / `RHI` 不驱动模拟

按 `ADR-0004`，renderer 与 `RHI` 只消费渲染数据并完成提交。

因此：

- 渲染帧率波动不应直接决定世界核心模拟步长
- RHI 提交完成与否不应反向修改世界推进语义
- renderer 可以读取提取后的渲染数据，但不直接调度世界

### 5.4 `resource` 在同步点并入，不直接打断主循环

按 `ADR-0007`，资源系统在 `M3+` 可能带来更多异步行为。

但这些行为的进入方式应是：

- 在受控同步点把加载完成结果并入 Runtime

而不是：

- 任意时间打断世界推进
- 任意线程直接改写世界 / renderer 状态

## 6. 当前明确不做的事情

### 6.1 不在本 ADR 中锁定最终 API 名称

本 ADR 不决定最终公开接口一定叫：

- `world.update`
- `runtime.step_frame`
- `runtime.run_stage`

它只锁定语义边界。

### 6.2 不在本 ADR 中承诺完整插值 / 回放 / 网络确定性

本 ADR 不承诺当前就实现：

- 渲染插值
- replay / rewind
- lockstep 网络确定性
- 完整 deterministic simulation 体系

它只为这些未来能力保留更健康的边界。

### 6.3 不在本 ADR 中锁定完整多线程执行图

本 ADR 不决定：

- 哪些系统并行执行
- scheduler 线程数
- job system 拆分粒度
- render thread 是否独立

这些属于更靠近实现与性能优化的议题。

### 6.4 不把后台回调当成世界更新入口

任何“资源加载完就直接回调改 world”“后台线程直接触发 gameplay 逻辑”的方案，都应视为偏离本 ADR，需要单独复审。

## 7. 后果

### 正面影响

- Runtime 主循环会更清晰，后续不容易长成不可控的大 while
- 固定步长模拟让移动、碰撞和输入行为更稳定
- Editor 未来的 pause / step / preview 能自然落在既有生命周期边界上
- 异步资源加载和后台任务被约束在可解释的同步点，不容易把状态边界打穿
- 与 `ADR-0005`、`ADR-0006`、`ADR-0007` 的边界能顺利拼起来

### 负面影响

- 当前要多承担一点执行模型设计纪律，不能用“先写个 while 跑起来再说”糊过去
- 固定步长模型在极低帧率下需要处理补偿步次数上限等细节
- 未来若要做更复杂的并行执行，还需要额外 ADR 或实现设计继续细化

### 约束性结论

- 后续任何把渲染帧间隔直接当作世界核心模拟 `dt` 的方案，都应视为偏离本 ADR，需要单独复审
- 后续任何把后台任务完成回调直接作为世界更新入口的方案，都应视为偏离本 ADR，需要单独复审
- 后续任何让对象逐个 `tick` 成为唯一不可替换主路径的方案，都应视为偏离本 ADR，需要单独复审

## 8. 相关决策

- **ADR-0001: 语言选型策略** — Runtime 高层执行控制更偏 Rust 侧承接，平台和底层时钟 / 窗口桥接优先由 Zig 侧承接
- **ADR-0002: 构建系统与项目结构** — `app/` 作为默认宿主入口，world / scheduler / resource 等模块围绕本执行模型协作
- **ADR-0004: RHI 抽象粒度** — renderer / RHI 不得反向支配世界推进语义
- **ADR-0005: 世界模型方向** — 世界更新由 Runtime 的统一调度边界驱动，不把对象逐个 `tick` 写死为唯一主路径
- **ADR-0006: 编辑器与 Runtime 边界** — Runtime 必须可 pause / step / stop，不能是不可外控黑盒
- **ADR-0007: 资源加载与资产边界** — 资源异步完成结果只能在受控同步点回流到 Runtime

---

## 9. 一句话结论

Kadath 的执行模型采用 **“外层变频驱动 + 内层固定步长模拟 + 明确阶段边界 + 受控同步点回流”** 的策略：宿主按平台节奏驱动 Runtime，世界按固定步长推进，渲染独立消费已提交状态，后台任务只能在明确同步点并入运行时。
